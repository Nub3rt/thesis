\section{Architecture}

The application has two layers: \textit{Model} and \textit{View}. Business logic is completely separated in the \textit{Model}, and is platform independent. This means that separate frontends could be developed for this one backend.\\
The main aspect during development was extensibility: there are multiple boards that can be played on, different decks using different cards, extensions which add new cards, new resources, or even new game features. In this documentation you can find multiple explanations for implementing new varieties.

View manages and renders the window, stores information for rendering and communicates with the \textit{Model}. My implementation used OpenGL for rendering.

The \textbf{App} class holds together the application: it stores \textit{View} instances, and injects instances of the \textit{Model} into the corresponding \textit{View} instance.

\textit{main.cpp} is the entry point for the application. It manages the following responsibilities:
\begin{compactitem}
    \item Initializing submodules and libraries.
    \item Instantiate and initialize an \textbf{App} instance.
    \item Run the \textit{render loop}. Here, it handles window events and forwards them to \textbf{App}, such as mouse and keyboard input. \textbf{App}'s \texttt{Update} and \texttt{Render} methods are called here.
    \item Clean up once the application is about to exit.
\end{compactitem}

\begin{figure}[H]
    \centering
    \includegraphics[width=0.5\textwidth]{package}
    \caption{Package diagram of the application}
    \label{fig:package}
\end{figure}

Each file is self-contained, and only includes headers from the standard library other than the project. All enumerated values are \textit{enum classes}.

There are some classes that have circular dependencies, for example \textbf{GameModel} and \textbf{GameModelState}. This was made possible with the following steps:
\begin{itemize}
    \item Create \textit{forward declaration headers} for the classes. This header should only have the declaration of it's class in it. Notice the naming of the file.
    \lstset{caption={game\_model.fwd.hpp}}
    \begin{lstlisting}[language={C++}]
namespace model
{
class GameModel;
}
    \end{lstlisting}
    \item In the header files, the first lines should be including every \textit{*.fwd.hpp} file that is involved in the circular dependency. Include the rest of the header files as normal. DO NOT include the normal header file of other classes in the circular dependency.
    \item In the \textit{*.cpp} files, include the normal headers of all the classes needed.
\end{itemize}

This structure solves these circular dependencies, however, there are a few drawbacks:

\begin{itemize}
    \item Since in the header files only the declaration of the other classes is present, no function calls can be made here. This means that inline functions cannot use the other classes.
    \item From the previous point, it is apparent that classes participating cannot be template classes, as these require all their definitions in their respective header files.
\end{itemize}

There is some leeway though: one header file from the two can include the other one. In this case, the structure of files and includes should still be upheld.

Every code in this project is under the namespace \textit{::model}.

To avoid magic numbers in the code, I have created a \textit{constants.hpp} header file, which consists of constants defined with \textit{inline constexpr}. This can be included from any other file - even from \textit{View}.

\subsubsection{The board}

The \textit{::model::boards} namespace contains the part of the code that implements the game board. Mars is made up of hexes, and to be more specific, the hexes have pointy-top orientation. Storing tables made up of hexes is not trivial, and there are multiple ways to implement it.

I choose to go with the axial coordinate system. Here every square has a $q$ and an $r$ coordinate. Increasing the $q$ coordinate moves right horizontally, and increasing the $r$ coordinate moves down, but instead of vertically, it moves on the line you get by rotating the $q$ axis $60^\circ$ in the negative direction. This alignment is matches with the usual layout in programming, where the $y$-axis is directed downwards.

It is important to note, that the axial coordinates are derived from cube coordinates, which have a third coordinate, $s$. But since the equation $q + r + s = 0$ is true for all tiles, we can identify each square with just two coordinates, and calculate $s$ if we need it.

\subsubsection*{Tile}

This class represents a single tile on the board. For convenience, they store their $q$ and $r$ positions, as well as their current type and owner. Oceans cannot be owned, but an empty tile can have an owner. Placement bonuses are also stored in each class and can be applied to the placer.

\subsubsection*{Boards}

To implement different boards in the application, I have decided to use the \textit{bridge design pattern}, as
\begin{compactitem}
    \item it hides the underlying data structure in the form of the implementor,
    \item it enables different board layouts and implementations, as classes can derive from the implementor, each one representing a different board variant, \textit{but} at the same time
    \item it makes the boards extensible, as classes can derive from the abstraction and implement functionality specific to them. Since we are deriving from the abstraction, all concrete implementors automatically gain this extended functionality.
\end{compactitem}

\begin{figure}[H]
    \centering
    \includegraphics[width=1.0\textwidth]{class_boards}
    \caption{Class diagram of the \textit{::model::boards} namespace.}
    \label{fig:class_boards}
\end{figure}

As Figure~\ref{fig:class_boards} shows, \textbf{ConcreteBoard}'s methods are almost all virtual or abstract. Board stores an instance of \textbf{ConcreteBoard}, and extends the interface of it with methods required for the game. A new board can simply be implemented by inheriting from \textbf{ConcreteBoard}. Here there are no such classes, but Board can also be derived from, to implement additional behavior, for example some functionality specific to an extension.

Since the game board as a whole is also hex shaped, the tiles do not make out a full rectangle. There are multiple solutions to storing a board, and each and every subclass of \textbf{ConcreteBoard} can implement their own.\\
For \textbf{TharsisConcreteBoard}, I choose the 2D array implementation shown on Figure~\ref{fig:board_memory}. I made this decision because indexing is easy and fast compared to other solutions and the elements don't move, they stay in memory for a full game, so after the initial allocation only fields of the elements are modified. This also means that the unused memory is negligible.

\subsubsection*{Iterators}

Notice the \texttt{begin} and \texttt{end} methods in the class diagram on Figure~\ref{fig:class_boards}. It was a requirement that boards could be iterated over. However, there were multiple obstacles I needed to overcome during the design and implementation of a universally usable iterator.

Since there could be any number of different board implementations, each one could potentially have a fundamentally different iterator. This sparked the interest to make an abstract \textbf{Iterator} base class, and derive iterators for every \textbf{ConcreteBoard} implementation.

But having \textbf{Iterator} as a base class meant that \texttt{begin} and \texttt{end} cannot simply return an \textbf{Iterator} instance because of object slicing\footnote{The derived class needs more memory than its parent class.}. The problem is, returning a pointer to an \textbf{Iterator} created by \textit{new} does not sound good either: nobody expects a pointer when they call \texttt{begin} on a container and no one expects that they need to call delete on it. This would just be bad design. Furthermore, it would be a pointer: the semantics for using the \textbf{iterator} would be different, and you could not even use it for a range-based for loop.

My solution: I created a child class of \textbf{Iterator} called \textbf{IteratorWrapper}. It has a constructor that takes an \textbf{Iterator} pointer - any one of our concrete iterators - automatically deletes it when \textbf{IteratorWrapper} goes out of scope, and delegates every operation to the \textbf{Iterator} it is holding.

\begin{figure}[H]
    \centering
    \includegraphics[width=1.0\textwidth]{class_iterators}
    \caption{Class diagram of the iterators.}
    \label{fig:class_iterators}
\end{figure}

There are advantages and disadvantages of subclassing \textbf{IteratorWrapper} from \textbf{Iterator}. On one hand, it enforces any change in the \textbf{Iterator} interface to be updated in \textbf{IteratorWrapper}. On the other hand, someone may accidentally assign an instance of \textbf{IteratorWrapper} to an \textbf{Iterator} variable, and object slicing happens. However, this has a really low probability, as these classes are enclosed in the \textbf{ConcreteBoard} class.

\subsubsection{Decks and cards}

The \textit{::model::decks} namespace contains classes implementing project cards, different sets of cards, and a \textbf{Deck} class. 

In the board game, each card has a unique name, and an ID by design. I imported these into the implementation, creating an enumerated type, \textbf{CardID}, where identifiers bear the name of the card, and have their values set to their respective ID.

\subsubsection*{Cards}

The game features three types of cards:

\begin{compactitem}
    \item \textbf{Event cards} (orange) only have effects when they are played, and after that they are turned face down. Their tags do not get counted for requirements. Victory points still count at the end of the game.
    \item \textbf{Automated cards} (green) also only have effects when they are played, but they stay face up and their tags are in effect for the rest of the game.
    \item \textbf{Active card} (blue) are similar to automated cards, but they either have an \textit{effect} or an \textit{action}.
    \begin{compactitem}
        \item \textit{Effect cards} have ongoing effects, that trigger automatically on specific events (e.g. when the player places a city they gain some resources, or all cards cost one less).
        \item \textit{Action cards} have an action, that the player can choose to perform once each generation. They may have a cost needed to perform said action.\\
        There can be multiple different actions on one card. In this case, only one of them can be used in each generation.
    \end{compactitem}
\end{compactitem}

Action cards have an associated enumerated type \textbf{Availability}, which represents their state:
\begin{compactitem}
    \item usable
    \item not usable
    \item used this generation
\end{compactitem}

\begin{figure}[H]
    \centering
    \includegraphics[width=1.0\textwidth]{class_cards}
    \caption{Class diagram of the cards.}

The tag system is implemented in the \textbf{Card} parent class. The private \textit{\_tags} member holds this information, and derived concrete classes should utilize The \texttt{AddTag} protected method in their constructors to configure the correct amount of tags.

The \textit{template method design pattern} is used a lot in these classes. \textbf{Card}'s other protected methods are all virtual, and they are used by the methods listed in the next paragraphs.

A card has some kind of state and state-dependent logic. These are the three states cards can have:
\begin{compactitem}
    \item The card is in the deck if $\_holder = nullptr \land \_owner = nullptr$
    \item The card is in the player's hand if $\_holder \neq nullptr \land \_owner = nullptr$
    \item The card was played by the player if $\_holder \neq nullptr \land \_owner \neq nullptr$
\end{compactitem}
The following methods have state-specific behaviour: \texttt{Buy}, \texttt{Sell}, \texttt{GetCost}, \texttt{CanBePlayed}, \texttt{Play} and \texttt{CountVPs}. \texttt{Buy} just sets \textit{\_holder} to the received parameter, and \texttt{Sell} sets it back to \textit{null}. This means that the credits received or paid have to be handled elsewhere. \texttt{GetCost} requires a holder as this calculates the cost with cost reductions from the holder's effect cards. \texttt{CanBePlayed} also requires a holder, and uses the virtual \texttt{SatisfiesRequirements} method. \texttt{CountVPs} requires an owner, as only then can victory points be awarded.

In this case, \texttt{DoPlayCard} gets passed as a function pointer to be called after payment confirmation.

The concrete cards are contained in the \textit{::model::decks::cards} namespace as to not pollute the \textit{::model::decks} namespace. Adding a new card can simply be done by creating a new class, inheriting from one of the four types of cards (\textbf{EventCard}, \textbf{AutomatedCard}, \textbf{ActiveCardWithEffect}, \textbf{ActiveCardWithAction}), calling the parent constructor with the appropriate parameters, calling \texttt{AddTag} in it for all the card's tags and overriding the appropriate methods. In the \textit{::model::decks::cards} namespace there is a header file located which includes all the cards. This way, when dealing with the concrete card classes one does not have to include them separately by hand.

\subsubsection*{The deck and deck providers}

In the course of the game, players can draw cards from a pile of cards - the deck - and sell - discard - cards they decide to. To enable multiple card sets for the game, I created a \textbf{DeckProvider} abstract class, which has one method, \texttt{GenerateDeck}, which returns a freshly created list of cards. This method has to be overridden in derived classes, returning a different set of cards for each subclass. These classes can even implement the \textit{singleton design pattern}.

An instance of the \textbf{DeckProvider} class can be injected into the \textbf{Deck} class. \textbf{Deck} initializes itself with the cards that \texttt{GenerateDeck} returns, shuffling them. \textbf{Card}s can be drawn from \textbf{Deck}, and discarded cards get stored in another member. When the deck is empty at card draw, discarded cards get shuffled and put back into the deck.

\subsubsection*{Event}

The model contains an \textbf{Event} class for event-driven programming. The board, the \textbf{Player} and the \textbf{GameModel} classes all feature events. However, this \textbf{Event} class is not really an event. It only stores one function, so at any time a maximum of one function can be subscribed to the event.

\subsubsection*{Player}

The player class stores data about a player. Resources, resource productions are stored in an array indexed by the target resource's underlying enumerated value. There are lots of events to make the program centralized: every time a player gains or does something, it comes in here. Methods usually have two kinds: the first invokes an event, notifying the \textbf{GameModel} about the requested change, and the latter one confirms and actually carries out the change (e.g. \texttt{RaiseTR} invokes an event, and \texttt{GainTR} modifies the \textit{\_tr} member in \textbf{Player}). There are also methods for handling card ownership and play.

\subsubsection*{Core Model}

The game leans heavily toward a state-centric architecture. The model was designed with this in mind from the start, and I am using the \textit{state design pattern}. As before, it is still important to make a construct that allows new game modes and variants to be implemented easily and following the SOLID design principles. I identified the following states during planning:

\begin{itemize}
    \item \textbf{Research state:} Corresponds to the research phase in the game. The player receives four cards, and can buy as many of them as they want, each costing 3 Credits.
    \item \textbf{Idle state:} Corresponds to the action phase in the game. The player can play cards, sell cards, use actions, use standard project, convert resources and end their turn.
    \item \textbf{Placement confirmation state:} Occurs whenever the player is placing a tile. A position is required for placing the tile, except when the card \textit{Noctis City} is played and the game board has a reserved tile for it. In this case the city gets placed automatically.
    \item \textbf{Payment confirmation state:} Occurs whenever the player chooses to perform an action that requires payment that can be paid for by Steel or Titanium resources (card playing, specific actions on cards) and he has at least one of the correct resource type. If they have at least one resource, this state will occur even if they can only afford the payment by spending all their Credits and resources, to give feedback to the player about the fact they are spending their resources.
    \item \textbf{Post last generation state:} After the last generation, players have the option to convert their Plant resources to greeneries as normal. This is the only action they can perform here. Placement bonuses still trigger. After this phase, the game is over.
    \item \textbf{Post last generation placement confirmation state:} Placing greeneries in post last generation state transition into this state for clarity instead of the normal placement confirmation state.
    \item \textbf{Game over state:} After the greenery converting phase, the game goes to this state. No actions are available here.
\end{itemize}

\textbf{GameModel} is an abstract class, that implements most of the features required for a usual game of Terraforming Mars. The base states inheriting from \textbf{GameModelState} were written for this abstract \textbf{GameModel}, which has virtual \texttt{CreateStateVariant} methods. Whenever a state change is about to happen and a new state instance has to be created, they get constructed through these methods. Different game variants can then inherit from \textbf{GameModel}, and if they need they can also create specialized state classes inheriting from the different \textbf{GameModelState} classes (or even from \textbf{GameModelState} itself). If they do, they need to override the appropriate \texttt{CreateStateVariant} method so that the model can create the correct state instance for the variant.

Let's go over this with the solo variant. \textbf{SoloGameModel} inherits from \textbf{GameModel}, and overrides some methods: the abstract \texttt{CreatePlayer} method, since starting terraform rating and resource productions varies between game modes. Turn ending logic is also different in solo games, so I created \textbf{SoloIdleState} and \textbf{SoloPostLastGeneration}, both inheriting from their respective parent classes.

Because only one tile can be placed at a time, but one action can result in multiple tile placements, there has to be some sort of mechanism that allows this behavior. For this, I created a \textbf{Request} base class in \textbf{GameModel}, and queue that stores pending request. In the idle state, if there is a request, it gets performed. In placement and payment confirmation state, after confirmation was received and there are requests, instead of going back to the idle state, the next request gets performed.

\begin{figure}[H]
    \centering
    \includegraphics[width=1.0\textwidth]{class_requests}
    \caption{Class diagram of the requests.}
    \label{fig:class_requests}
\end{figure}

For performing the next request, I use the \textit{visitor design pattern}. After popping the next request from the queue, the abstract method \texttt{Perform} gets called, in which every subclass calls the state's \texttt{PerformRequest} overloaded method with \textit{this} as argument.

There is a flaw in this design: you cannot directly change the state from a state method, as it can result in dangling references in the call stack. This cannot be solved with \textit{std::shared\_ptr}, as its reference counter does not increase on method calls on the held object.

To solve this, I created the \texttt{RequestStateChange} method, which sets \textit{\_next\_state} to the parameter, and created an \texttt{Update} method which sets the state to the new one. This means that the model has an update method that has to be called frequently, in a render loop probably, which is far from optimal.

\section{Architecture}

The application has two layers: \textit{Model} and \textit{View}. Business logic is completely separated in the \textit{Model}, and is platform independent. This means that separate frontends could be developed for this one backend.

The main aspect during development was extensibility: there are multiple boards that can be played on, different decks using different cards, extensions which add new cards, new resources, or even new game features. In this documentation you can find multiple explanations on how to implement these new varieties.

Since the game utilizes random chance (e.g. for card drawing), another aspect was that the application could be seeded, so that given the same seed for the game, the same random events happen.

View manages and renders the window, stores information for rendering and communicates with the \textit{Model}. My implementation uses OpenGL for rendering.

The \textbf{App} class holds together the application: it stores \textit{View} instances, and injects instances of the \textit{Model} into the corresponding \textit{View} instance.

\textit{main.cpp} is the entry point for the application. It manages the following responsibilities:
\begin{compactitem}
    \item Initializing submodules and libraries.
    \item Instantiate and initialize an \textbf{App} instance.
    \item Run the \textit{render loop}. Here, it handles window events such as mouse and keyboard input, and forwards them to \textbf{App}. It is also responsible for calling the \texttt{Update} and \texttt{Render} methods of the \textbf{App} instance on each frame.
    \item Clean up once the application is about to exit.
\end{compactitem}

The package diagram of the solution can be seen in Figure~\ref{fig:package}.

\begin{figure}[H]
    \centering
    \includegraphics[width=0.5\textwidth]{package}
    \caption{Package diagram of the application.}
    \label{fig:package}
\end{figure}

Each file is self-contained, and only includes headers from the standard library other than the project. All enumerated values are \textit{enum classes}.

There are some classes that have circular dependencies, for example \textbf{GameModel} and \textbf{GameModelState}. This was made possible with the following steps:
\begin{itemize}
    \item Create \textit{forward declaration headers} for the classes. This header should only have the declaration of it's class in it. Notice the naming of the file.
    \lstset{caption={game\_model.fwd.hpp}}
    \begin{lstlisting}[language={C++}]
namespace model
{
class GameModel;
}
    \end{lstlisting}
    \item In the header files, the first lines should be including every \textit{*.fwd.hpp} file that is involved in the circular dependency. Include the rest of the header files as normal. DO NOT include the normal header file of other classes in the circular dependency.
    \item In the \textit{*.cpp} files, include the normal headers of all the classes needed.
\end{itemize}

This structure solves these circular dependencies, however, there are a few drawbacks:

\begin{itemize}
    \item Since in the header files only the declaration of the other classes is present, no function calls can be made here. This means that inline functions cannot use the other classes.
    \item From the previous point, it is apparent that classes participating cannot be template classes, as these require all their definitions in their respective header files.
\end{itemize}

There is some leeway though: one header file from the two can include the other one. In this case, the structure of files and includes should still be upheld.

\subsection{Model}

Every code in this project is under the namespace \textit{::model}.

To avoid magic numbers in the code, I have created a \textit{constants.hpp} header file, which consists of constants defined with \textit{inline constexpr}. This can be included from any other file - even from \textit{View}.

The central unit of the model is the \textbf{GameModel} class. It is what users of this library will interact with. Other classes in the namespace exist to help this class.

\subsubsection{The board}

The \textit{::model::boards} namespace contains the part of the code that implements the game board. Mars is made up of hexagonal tiles (hexes), and to be more specific, hexes that have pointy-top orientation. Storing tables made up of hexes is not trivial, and there are multiple ways to implement it. More can be read about this topic from the article written by Amit Patel\cite{patel2013hex}.

I choose to go with the axial coordinate system shown in Figure~\ref{fig:axial}. Here every square has a $q$ and an $r$ coordinate. Increasing the $q$ coordinate moves right horizontally, and increasing the $r$ coordinate moves down, but instead of vertically, it moves on the line you get by rotating the $q$ axis $60^\circ$ in the negative direction. This alignment matches the usual layout in programming, where the $y$-axis is directed downwards.

\begin{figure}[H]
    \centering
    \includegraphics[width=0.8\textwidth]{axial}
    \caption{The axial coordinate system. Notice the third coordinate in a lighter color.}
    \label{fig:axial}
\end{figure}

It is important to note, that the axial coordinates are derived from cube coordinates, which have a third coordinate, $s$. But since the equation $q + r + s = 0$ is true for all tiles, we can identify each square with just two coordinates, and calculate $s$ if we need it.

The \textit{::model::boards} namespace has one enumerated data type, \texttt{TileType}. Its values can be seen on Figure~\ref{fig:class_boards}.

\subsubsection*{Tile}

This class represents a single tile on the board. For convenience, they store their $q$ and $r$ positions, as well as their current type and owner. Oceans cannot be owned, but an empty tile can have an owner. Placement bonuses are also stored in each class and can be applied to the player placing the tile.

\subsubsection*{Boards}

To implement different boards in the application, I have decided to use the \textit{bridge design pattern}\cite{gamma1994design}, as it has the following advantageous properties:
\begin{compactitem}
    \item it hides the underlying data structure in the form of the implementor,
    \item it enables different board layouts and implementations, as classes can derive from the implementor, each one representing a different board variant, \textit{but} at the same time
    \item it makes the boards extensible, as classes can derive from the abstraction and implement functionality specific to them. Since we are deriving from the abstraction, all concrete implementors automatically gain this extended functionality.
\end{compactitem}

\begin{figure}[H]
    \centering

As Figure~\ref{fig:class_boards} shows, \textbf{ConcreteBoard}'s methods are almost all virtual or abstract. Board stores an instance of \textbf{ConcreteBoard}, and extends the interface of it with methods required for the game. A new board can simply be implemented by inheriting from \textbf{ConcreteBoard}. Here there are no such classes, but Board can also be derived from, to implement additional behavior, for example some functionality specific to an extension.

Since the game board as a whole is also hex shaped, the tiles do not make out a full rectangle. There are multiple solutions to storing a board, and each and every subclass of \textbf{ConcreteBoard} can implement their own. \\
For \textbf{TharsisConcreteBoard}, I chose the 2D array implementation shown in Figure~\ref{fig:board_memory}. I made this decision because indexing is easy and fast compared to other solutions and the elements don't move, they stay in memory for a full game, so after the initial allocation only fields of the elements are modified. This also means that the unused memory is negligible. Furthermore, special off-board tiles can be stored on the empty ones.

\subsubsection*{Iterators}

Notice the \texttt{begin} and \texttt{end} methods in the class diagram in Figure~\ref{fig:class_boards}. It was a requirement that boards could be iterated over. However, there were multiple obstacles I needed to overcome during the design and implementation of a universally usable iterator.

Since there could be any number of different board implementations, each one could potentially have a fundamentally different iterator. This sparked the interest to make an abstract \textbf{Iterator} base class, and derive iterators for every \textbf{ConcreteBoard} implementation.

But having \textbf{Iterator} as a base class meant that \texttt{begin} and \texttt{end} cannot simply return an \textbf{Iterator} instance because of object slicing. Object slicing happens, when an instance of a derived class gets assigned to its parent type: the variables declared in the derived class will be lost because the parent type has a smaller size than the derived type. Trying to access members of the derived type after the assignment would read from memory beyond the variable, which results in undefined behavior.

The problem is, returning a pointer to an \textbf{Iterator} can be misleading. Even more so if it was created by \textit{new}: nobody expects a pointer when they call \texttt{begin} on a container and no one expects that they need to call delete on it. This would just be bad design. Furthermore, it would be a pointer: the semantics for using the iterator would be different, as you need to dereference the pointer, and you could not even use it for a range-based for loop.

My solution: I created a child class of \textbf{Iterator} called \textbf{IteratorWrapper}, as depicted in Figure~\ref{fig:class_iterators}. It has a constructor that takes an \textbf{Iterator} pointer - any one of our concrete iterators - automatically deletes it when \textbf{IteratorWrapper} goes out of scope, and delegates every operation to the \textbf{Iterator} it is holding.

\begin{figure}[H]
    \centering
    \includegraphics[width=1.0\textwidth]{class_iterators}
    \caption{Class diagram of the iterators.}
    \label{fig:class_iterators}
\end{figure}

There are advantages and disadvantages of subclassing \textbf{IteratorWrapper} from \textbf{Iterator}. On one hand, it enforces any change in the \textbf{Iterator} interface to be updated in \textbf{IteratorWrapper}. On the other hand, someone may accidentally assign an instance of \textbf{IteratorWrapper} to an \textbf{Iterator} variable, and object slicing happens. However, this has a really low probability, as these classes are enclosed in the \textbf{ConcreteBoard} class.

\subsubsection{Decks and cards}

The \textit{::model::decks} namespace contains classes implementing project cards, different sets of cards, and a \textbf{Deck} class. 

In the board game, each card has a unique name, and an ID by design. I imported these into the implementation, creating an enumerated type, \textbf{CardID}, where identifiers bear the name of the card, and have their values set to their respective ID.

\subsubsection*{Cards}

The game features three types of cards:

\begin{compactitem}
    \item \textbf{Event cards} (orange) only have effects when they are played, and after that they are turned face down. Their tags do not get counted for requirements. Victory points given by the card still count at the end of the game.
    \item \textbf{Automated cards} (green) also only have effects when they are played, but they stay face up and their tags are in effect for the rest of the game.
    \item \textbf{Active card} (blue) are similar to automated cards, but they either have an \textit{effect} or an \textit{action}.
    \begin{compactitem}
        \item \textit{Effect cards} have ongoing effects, that trigger automatically on specific events (e.g. when the player places a city they gain some resources, or all cards cost one less).
        \item \textit{Action cards} have an action, that the player can choose to perform once each generation. They may have a cost needed to perform said action. \\
        There can be multiple different actions on one card. In this case, only one of them can be used in each generation.
    \end{compactitem}
\end{compactitem}

Action cards have an associated enumerated type \textbf{Availability}, which represents their state:
\begin{compactitem}
    \item usable,
    \item not usable,
    \item used this generation.
\end{compactitem}

The full class diagram can be examined in Figure~\ref{fig:class_cards}.

The tag system is implemented in the \textbf{Card} parent class. The private \textit{\_tags} member holds this information, and derived concrete classes should utilize The \texttt{AddTag} protected method in their constructors to configure the correct amount of tags.

The \textit{template method design pattern}\cite{gamma1994design} is used a lot in these classes. \textbf{Card}'s other protected methods are all virtual, and they are used by the methods listed in the next paragraphs.

A card has some kind of state and state-dependent logic as indicated in Figure~\ref{fig:state_cards}. These are the three states cards can have:
\begin{compactitem}
    \item The card is in the deck if $\_holder = nullptr \land \_owner = nullptr$
    \item The card is in the player's hand if $\_holder \neq nullptr \land \_owner = nullptr$
    \item The card was played by the player if $\_holder \neq nullptr \land \_owner \neq nullptr$
\end{compactitem}
The following methods have state-specific behaviour: \texttt{Buy}, \texttt{Sell}, \texttt{GetCost}, \texttt{CanBePlayed}, \texttt{Play} and \texttt{CountVPs}. \texttt{Buy} just sets \textit{\_holder} to the received parameter, and \texttt{Sell} sets it back to \textit{null}. This means that the credits received or paid have to be handled elsewhere. \texttt{GetCost} requires a holder as this calculates the cost with cost reductions from the holder's effect cards. \texttt{CanBePlayed} also requires a holder, and uses the virtual \texttt{SatisfiesRequirements} method. \texttt{CountVPs} requires an owner, as only then can victory points be awarded.

\subsubsection*{The deck and deck providers}

In the course of the game, players can draw cards from a pile of cards - the deck - and sell/discard cards they decide to. To enable multiple card sets for the game, I created a \textbf{DeckProvider} abstract class, which has one method, \texttt{GenerateDeck}, which returns a freshly created list of cards. This method has to be overridden in derived classes, returning a different set of cards for each subclass. These classes can even implement the \textit{singleton design pattern}\cite{gamma1994design}.

An instance of the \textbf{DeckProvider} class can be injected into the \textbf{Deck} class. \textbf{Deck} initializes itself with the cards that \texttt{GenerateDeck} returns, shuffling them. \textbf{Card}s can be drawn from \textbf{Deck}, and discarded cards get stored in another member. When the deck is empty at card draw, discarded cards get shuffled and put back into the deck. The full class diagram of this namespace can be seen in Figure~\ref{fig:class_decks}.

\subsubsection*{Core Model}

The game leans heavily toward a state-centric architecture. The model was designed with this in mind from the start, and I am using the \textit{state design pattern}\cite{gamma1994design}. As before, it is still important to make a construct that allows new game modes and variants to be implemented easily and following the open-closed principle. I identified the following states during planning:

\begin{itemize}
    \item \textbf{Research state:} Corresponds to the research phase in the game. The player receives four cards, and can buy as many of them as they want, each costing 3 Credits.
    \item \textbf{Idle state:} Corresponds to the action phase in the game. The player can play cards, sell cards, use actions, use standard project, convert resources and end their turn.
    \item \textbf{Placement confirmation state:} Occurs whenever the player is placing a tile. A position is required for placing the tile, except when the card \textit{Noctis City} is played and the game board has a reserved tile for it. In this case the city gets placed automatically.
    \item \textbf{Payment confirmation state:} Occurs whenever the player chooses to perform an action that requires payment that can be paid for by Steel or Titanium resources (card playing, specific actions on cards) and he has at least one of the correct resource type. If they have at least one resource, this state will occur even if they can only afford the payment by spending all their Credits and resources, to give feedback to the player about the fact they are spending their resources.
    \item \textbf{Post last generation state:} After the last generation, players have the option to convert their Plant resources to greeneries as normal. This is the only action they can perform here. Placement bonuses still trigger. After this phase, the game is over.
    \item \textbf{Post last generation placement confirmation state:} Placing greeneries in post last generation state transition into this state for clarity instead of the normal placement confirmation state.
    \item \textbf{Game over state:} After the greenery converting phase, the game goes to this state. No actions are available here.
\end{itemize}

\textbf{GameModel} is an abstract class, that implements most of the features required for a usual game of Terraforming Mars. Part of the class diagram is displayed in Figure~\ref{fig:class_gamemodel}. The base states inheriting from \textbf{GameModelState} were written for this abstract \textbf{GameModel}, which has virtual \texttt{CreateStateVariant} methods. Whenever a state change is about to happen and a new state instance has to be created, they get constructed through these methods. Different game variants can then inherit from \textbf{GameModel}, and if they need they can also create specialized state classes inheriting from the different \textbf{GameModelState} classes (or even from \textbf{GameModelState} itself). If they do, they need to override the appropriate \texttt{CreateStateVariant} method so that the model can create the correct state instance for the variant.

Figure~\ref{fig:state_sologamemodel} provides a visualization of the solo variant. \textbf{SoloGameModel} inherits from \textbf{GameModel}, and overrides some methods: the abstract \texttt{CreatePlayer} method, since starting terraform rating and resource productions varies between game modes. Turn ending logic is also different in solo games, so I created \textbf{SoloIdleState} and \textbf{SoloPostLastGeneration}, both inheriting from their respective parent classes.

Because only one tile can be placed at a time, but one action can result in multiple tile placements, there has to be some sort of mechanism that allows this behavior. For this, I created a \textbf{Request} base class in \textbf{GameModel} as represented in Figure~\ref{fig:class_requests}, and a queue that stores pending request. In the idle state, if there is a request, it gets performed. In placement and payment confirmation state, after confirmation was received and the request queue is not empty, instead of going back to the idle state, the next request gets performed.

\begin{figure}[H]
    \centering
    \includegraphics[width=1.0\textwidth]{class_requests}
    \caption{Class diagram of the requests.}
    \label{fig:class_requests}
\end{figure}

For performing the next request, I use the \textit{visitor design pattern}\cite{gamma1994design}. After popping the next request from the queue, the abstract method \texttt{Perform} gets called, in which every subclass calls the state's \texttt{PerformRequest} overloaded method with \textit{this} as argument.

There is a flaw in this design: you cannot directly change the state from a state method, as it can result in dangling references in the call stack. This cannot be solved with \textit{std::shared\_ptr}, as its reference counter does not increase on method calls on the held object.

To solve this, I created the \texttt{RequestStateChange} method, which sets \textit{\_next\_state} to the parameter, and created an \texttt{Update} method which sets the state to the new one. This means that the model has an update method that has to be called frequently, in a render loop probably, which is far from optimal. Resolving this issue is an important task for the future.

\subsubsection*{GL utils}

Some code was borrowed from the computer graphics team, mainly \textit{gl\_utils.*}, \textit{camera.\*} and \textit{spherical\_camera\_manipulator.\*}. I created an interface for camera manipulators and implemented a bobbing camera manipulator that "follows" the mouse on the game screen.

\subsubsection*{Text rendering}

The application needed some way to render text to the screen. For this, I implemented the \textbf{TextRenderer} static class. The base structure comes from the LearnOpenGL website by Joey de Vries\cite{learnopengl}. I have tweaked it to adapt it to my usage of OpenGL, and added some functionality, like centered text rendering. Note that this class can only render one line texts. At this point, only the first 128 characters of the ASCII character set can be rendered, other characters get rendered as a \texttt{?}.

\subsubsection*{Animatable}

For user experience and enjoyment, it is important that changes are smoothly animated, and not just abruptly appear on-screen. OpenGL provides no tools for this, so I had to implement tools for this from scratch. Luckily, GLM comes with a variety of easing functions\cite{ease} that we can use for our animations.

The \textit{animatable.hpp} header contains two templated data structures as seen in Figure~\ref{fig:class_animations}. \textbf{AnimationParams} is a simple template struct, containing the start and end value of an animation and the duration and elapsed time in seconds. \textbf{Animatable} is a template class which provides richer features for working with events.

At all times \textbf{Animatable} stores the current value it's holding. The type of \textit{\_value} is \textbf{T} which is the template parameter of \textbf{Animatable}. It can be accessed with the indirection operator and the structure dereference operator (\texttt{*} and \texttt{->}). The value can be set at any time with the \texttt{Set} method, but this clears any ongoing animation. The class also contains an easing function, that can be set at any point. Its default value is linear interpolation. \\
There can either be an ongoing animation effecting this value, or not. This is expressed with the member \textit{\_animation} of type \textbf{std::optional<AnimationParams<T>{}>}. When this optional contains a value, an animation is ongoing. \\
An animation can be set in two ways. \texttt{SetAnim} takes a start and end value and a duration. It clears any ongoing animation, and starts a new animation with the supplied parameters. \texttt{UpdateAnim} on the other hand takes in the end value only, a duration and a boolean value \textit{force\_time} indicating to whether or not force duration override.
\begin{compactitem}
    \item If there is no animation ongoing, a new animation is set, where the start is the current value of the \textbf{Animatable}, the end is the parameter of the method, and the duration also.
    \item If there is an ongoing animation, the end value is updated to the parameter of the method. If \textit{force\_time} is true, the elapsed value gets reset to zero, and the duration gets set to the duration parameter.
\end{compactitem}
The class features an \texttt{Update} method that takes the delta time, and updates the value based on the animation and the easing function. If the duration is over, it sets the value to the end value and clears the animation.

    \centering

    \caption{Class diagram of animation utilities.}
    \label{fig:class_animations}
\end{figure}

Since in the application we deal with colors, positions and much more that consist of vector data, it was required that \textbf{glm::vecX} types could be animated too. I solved this with template specialization. in Figure\ref{fig:class_animations}, the template specialization for \textbf{glm::vec3} is shown. An \textbf{Animatable<float>} is stored for each item of the vector. The base methods call their respective methods on each of the animatables. They are also public, so each one can be accessed and set independently. The value is also stored in an auxiliary \textit{\_value} member.

\subsubsection*{TileWrapper}

This class wraps one field of the game board. Information for rendering is stored here.

\subsubsection*{CardWrapper}

This class wraps a card. It features a state in the form of an enumerated type, which features the following values: \texttt{IDLE}, \texttt{HOVERED}, \texttt{DRAGGING}, \texttt{DRAWING} and \texttt{TO\_HAND}. Another enumerated type \textbf{Visual} stores what kind of visual effect the card currently has. It can have the following values: \texttt{NONE}, \texttt{HIGHLIGHT}, \texttt{ACTION\_HIGHLIGHT}, \texttt{SELL\_HIGHLIGHT} and \texttt{FADED}.

Data for rendering is stored also, for example position, scale, and rotate. These are an instance of \textbf{Animatable}. The class implements methods to set all the easing functions at once.

\textbf{MenuView} implements \textbf{View}. This view renders the menu screen, with a title, new game and quit buttons, and if there is an ongoing game, a continue button. \subsubsection*{App}

The \textbf{App} class holds together the application. It stores an instance of \textbf{MenuView} and optionally an instance of \textbf{GameView}. It features a \textit{\_current\_view} member, which it updates and renders. But it is important to call \texttt{Resize} on every living \textbf{View} instance.

\subsubsection*{Builder}

To create a \textbf{GameView} that is populated with its respective \textbf{GameModel} which also needs to be initialized with a \textbf{DeckProvider} and a \textbf{Board}, I used the \textit{builder design pattern}\cite{gamma1994design} to separate the construction of this complex object stack.

\textbf{MenuView} uses \textbf{Builder} to create a new \textbf{GameView} when new game is pressed. After that, it passes the created instance back to \textbf{App}.

\subsubsection*{\textit{main.cpp}}

The entry point of the application. It initializes subsystems, libraries and contexts. It creates an instance of the \textbf{App} class and initializes it. After these configurations, it runs the render loop, in which the following steps get performed:
\begin{itemize}
    \item Processes every event from SDL. Most of them get passed down to \textbf{App} also.
    \item Call \texttt{Update} on \textbf{App}.
    \item Call \texttt{Render} on \textbf{App}.
    \item Call \texttt{RenderGUI} on \textbf{App}.
    \item Finish rendering by swapping the framebuffers.
\end{itemize}

\subsubsection{Animations}

Using \textbf{Animatable}, we can create multiple animations. Since one action (like playing a card) can result in a lot of things happening (raising parameters, gaining resources, placing a tile all because of one card) I implemented an animation queue, where every animation has a set interval until the next animation cannot be started.

So \textbf{Animation} is an abstract class, that implements this behavior. The constructor takes an optional \textit{lockout\_time} duration parameter. The update method handles the decreasing of this member, and then calls the abstract method \texttt{DoUpdate}. The class also contains two optional callables, that get called when the animation starts and ends.

The \texttt{Render} abstract method is what renders the animation. This is implemented with the \textit{visitor design pattern}\cite{gamma1994design}: when \textbf{GameView} wants to render an animation, it calls this method, in which the children classes can call back the \texttt{RenderAnimation} with themselves as the parameter.

Concrete animations can then be derived from this class. For example, the \textbf{TextAnimation} class features a string to render, and its position, color and scale all wrapped in an instance of \textbf{Animatable}. \texttt{DoUpdate} calls \texttt{Update} on the animatables. Rendering is done with the current values from the animatables. \\
However, this class is pretty flexible, and can be used many ways. For example, \textbf{CardAnimation} only renders once, and it sets the respective \textbf{CardWrapper}'s animatable properties' animations.

In \textbf{GameView}, there is an animation queue with the pending animation, a vector with ongoing animations, and an \textbf{std::optional<Animation*>} which is the animation that currently locks, meaning no animation can be started. These are updated in every loop by the following steps:
\begin{itemize}
    \item Every ongoing animation gets processed: If it is over, it gets removed from the vector and deleted, else it gets updated.
    \item If there is a locking animation: if it still has time from its lockout, it simply gets updated, else it gets transferred to the ongoing animations, and updated (if it is not over already in which case it just gets deleted).
    \item While there is no locking animation and the animation queue is not empty: the next animation gets popped from the queue. If it has a lockout duration, it gets assigned to be the next lockout animation, else it gets added to the ongoing animations.
\end{itemize}

There is also an implemented but unused feature: animations can be put in a collection with a delay. While the delay is not over, they do nothing. Once the delay is over, they get transferred to the ongoing animations. This feature doesn't support lockout.

\subsubsection{Rendering}

\subsubsection*{App}

\textbf{App} contains the camera for the application. During rendering, the first thing rendered is the skybox. This always gets rendered, so \textbf{App} handles this. The skybox is slowly rotated to achieve a deeper space feeling.

\subsubsection*{Mouse picking}

By default, OpenGL provides three framebuffers that store render data.
\begin{itemize}
    \item The color buffer has three float values for every pixel, ranging from 0 to 1. This is the frame being rendered, each of the three values corresponding to one of the tree colors: red, green and blue.
    \item The depth buffer usually has 24 bits for every pixel. It is used to detect if the pixel being drawn is behind the already rendered pixel.
    \item The stencil buffer usually has 8 bits, so its values can range from 0 to 255. It can be used for various different rendering tricks and after-effects.
\end{itemize}

I used the stencil buffer for mouse picking. Each clickable element has an associated ID, and on a mouse down, mouse up or mouse move event we can poll the current value of the corresponding pixel of the stencil buffer. This way, we can identify which element was clicked or hovered over.

What ID to render can be set with the \texttt{SetStencilRef} method, but after rendering, it has to be set back to its original value, by calling \texttt{SetStencilRef} again without a parameter.

\subsubsection*{Menu}

On the menu screen, the title and three buttons need to be rendered. These are pre-made \textit{.png} files, as during the transition they need to be rendered 3D. The three buttons can be hovered and clicked.

\subsubsection*{Game}

First the game board is rendered. The board is rendered tile by tile. A Mars terrain is textured over the whole board, and this is offset horizontally and vertically by a random amount each game. The ocean and greenery textures are also projected onto the whole board, and the ocean is moving slowly. There are a few 3D tile types, their types are generated randomly. Lastly, the placement bonuses and player ownership indicating icons get drawn above the tiles. Lighting is achieved using the Phong modell\cite{bui1975illumination}.

Before rendering the HUD, the depth buffer is cleared, as everything here has to overlay what has been rendered so far. First the generation counter, menu button, end button, standard projects, global parameters and resources get rendered. After that, any state-specific rendering is carried out by calling \texttt{Render} on the current state. After that, the card panels get rendered, then the hand, and finally the animations.

HUD rendering is basically 2D rendering, so it does not use the camera. Positions and sizes are calculated dynamically and relative to the window and window size.

Cards and resources get their textures from sprite sheets. Card textures are derived from their \textbf{CardID}'s underlying value. Vertical and horizontal indices and strides are calculated in code, then get passed to the shaders with uniforms.

Cards can have a colored highlight around them. This was done in the fragment shader. If the alpha value is big, a highlight will be drawn. The alpha value of the highlight is based on the distance from the edge. The threshold that represents the highlight being a solid color moves in and out to create a pulsating effect.

The debug window allows the user to set a seed for their game. Starting two games with the same seed means the random tiles will generate to the same place, and cards will come in the same sequence.

The debug window allows the user to give themselves resources, resource production, raise their terraform rating, draw cards, raise temperature, raise oxygen and place ocean, greenery or city tiles. \\

Pressing \textbf{F3} toggles the basic camera and the editorial camera. With the editorial camera, the user can use look around with the mouse and fly around with the following keys: \textbf{A}, \textbf{W}, \textbf{S}, \textbf{D}, \textbf{E}, \textbf{Q}\footnote{A - left, W - forward, S - back, D - right, E - up, Q - down}.
